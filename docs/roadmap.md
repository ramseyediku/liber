# Roadmap

## Migrate to Claude API + Supabase (supersedes the on-device LLM sections below)

Replaced the on-device WebLLM engine (`src/shared/llmEngine.js` +
`src/offscreen/`, built and tuned across the entire "Capture flow rewrite"
history further down this file) with a Supabase Edge Function that calls
the Claude API server-side, and replaced `browser.storage.local`-only data
(jobs, profile) with Supabase (Postgres + Auth). Requested directly by the
project owner, not a response to a bug — everything below the on-device
engine's own problems (WebGPU/device support, model download size, the
Offscreen Document/Worker plumbing) is now moot, since extraction no longer
runs on-device at all. See `docs/architecture.md` for the current design
(`src/shared/extraction.js`, `src/shared/supabaseClient.js`, the rewritten
`src/shared/storage.js`).

Key decisions, both made explicitly by the project owner before
implementation (not inferred):

- **The extension calls a Supabase Edge Function, not Anthropic directly.**
  `ANTHROPIC_API_KEY` lives only as a Supabase project secret
  (`supabase secrets set`) — never inside the extension's own files, where
  it would be trivially extractable from an installed copy. The extension
  only ever holds the public Supabase anon key.
- **Supabase Auth + Postgres are now the source of truth for jobs/profile**,
  reversing v0.1's "local-only, no account" non-goal (see
  `docs/product-spec.md`). Real accounts, not an anonymous per-install id.

**The Supabase schema is owned and maintained by the project owner, not
generated by this change** — `storage.js` was written to match an existing
`job_profiles`/`jobs` schema (plus unused-for-now `site_structures`/
`entitlements` tables) rather than a schema designed alongside this code.
Three real mismatches between that schema and the old local-only data
model had to be resolved, each a deliberate choice rather than a guess:

- **No table for the user's own name/profession.** Stored in the Supabase
  Auth user's own `user_metadata` (`supabase.auth.updateUser({data:
  {...}})`) instead of a new table — no schema change needed, and it's
  naturally scoped to the signed-in user already.
- **`jobs.profile_id` is `NOT NULL`, referencing `job_profiles`** (a
  user's named job-search categories, e.g. "Software roles") — there's no
  UI for picking/creating one yet. `storage.js`'s `addJob` auto-creates
  (and reuses) a single `"General"` `job_profiles` row per user on first
  save. Revisit once real multi-profile UI exists — right now every job a
  user saves lands in the same one category regardless of what it's for.
- **The schema's `status` enum differs from the old one**: `applied`,
  `interviewing`, `offer`, `rejected`, `withdrawn` — no `ghosted`, plus two
  new values (`offer`, `withdrawn`) the dashboard didn't have colors for
  before. `STATUS`/`STATUS_META` (`storage.js`) and the status pill/dot CSS
  (`dashboard-shared.css`, `_base.css`'s color tokens) were updated to
  match.

**Deliberately deferred, not forgotten:**

- **`site_structures`** (a shared, cross-user, versioned cache of learned
  per-hostname selectors, written only by a service-role Edge Function) —
  the extension doesn't read or write it yet. Every save still goes
  JSON-LD first, then the Claude Edge Function, exactly as before this
  table existed. Wiring it in (checking for an active structure for the
  current hostname before falling back to Claude) is a real near-term
  opportunity — it would cut Claude API calls on sites with a validated
  structure — but needs the Edge Function's learn/validate/promote logic
  finalized first.
- **`entitlements`** (paid/unpaid, `source: 'extensionpay'`) — nothing
  gates on this yet. No feature currently checks `paid` before running;
  wiring a paywall (e.g. requiring `paid = true` before calling the
  extraction Edge Function) is a separate, later task.
- **No DB-level dedup constraint.** Unlike the old local-only design's
  in-memory Set check, the given schema has no unique index backing
  `jobTitle`+`company`+`location` uniqueness — `addJob`'s pre-check
  (`getAllJobs()` then a Set membership test) is the only thing enforcing
  it now, so a true race between two concurrent saves of the same job
  could in theory still insert twice. Not engineered around with a DB
  constraint that isn't part of the schema as given.

**`extraction.js`'s Edge Function name/payload shape is a placeholder**
(`EXTRACT_FUNCTION_NAME = "extract-job-fields"`), pending the real Edge
Function. Update it to match once that lands.

**Not yet exercised against a live backend.** This migration was
implemented and unit-tested (`npm test`) but not run end-to-end against a
real Supabase project/Claude API call from this environment — verify the
full sign-up → apply-click → consent → save flow manually once `.env` is
filled in (`npm run config`) and the Edge Function is deployed.

## Minimizing on-device LLM usage — superseded

**Superseded by "Migrate to Claude API + Supabase" above** — there's no
on-device engine left to minimize the RAM/CPU/GPU cost of. Left as
historical context for the on-device engine's own design history.

Added a batch of changes aimed specifically at the LLM's RAM/CPU cost on
low-end machines (e.g. a Chromebook with many tabs open) — see
`docs/architecture.md`'s "Minimizing on-device LLM usage" for the full
design. Two of them are deliberate reversals/tradeoffs worth flagging
explicitly rather than treating as free wins:

- **Lazy loading reverses the previous eager-warmup design.** Model
  loading used to be triggered as early and as often as possible
  (`onInstalled`, `onStartup`, onboarding submit, every dashboard open —
  see the now-superseded description this replaced, below) specifically
  to avoid a cold model on the first apply click. That's gone: `warmup()`
  is now triggered only once `content.js`'s listing check confirms an
  actual single-job apply flow is starting. This means a session that
  goes a while between applies (or unloads the engine via the idle
  timeout/completion triggers below) pays the "upload cached weights to
  GPU" cost again on the next one — mitigated by the on-page progress
  badge (`content.js`), and by the fact that the weight *download* itself
  is unaffected (WebLLM's Cache API cache persists regardless of when
  `warmup()` is first called), but not eliminated. Chosen because the
  stated goal — minimal idle RAM/GPU footprint on low-end machines — only
  works if the model isn't loaded by default for installs that never end
  up applying to anything in a session.
- **The URL-keyed extraction cache (`background.js`'s
  `urlExtractionCache`) can under-refresh a same-URL, in-place SPA wizard
  step.** Nothing distinguishes "same URL, same content" from "same URL,
  next step" at the cache-lookup point, so a site that swaps its form
  content in place without navigating or opening a modal (the
  `SETTLE_WINDOW_MS` fallback path) would get served the first step's
  cached result on a later one. Not seen in practice yet — most
  multi-step flows either navigate or open a modal — flagged rather than
  engineered around further, same spirit as the rest of this file.

**Partially revisited for the post-signup setup page.** `onboarding.js`
now also triggers `warmup()` unconditionally at page load (not gated on
an apply flow), to get a head start on the one-time load before the
user's first apply click — see "Post-signup setup page" below. This
doesn't reopen the RAM-minimization problem above: `background.js`'s
`LIBER_LLM_WARMUP` handler now sets `lastLlmActivityAt` on *every* call,
not just inside `handleFlowStep`, so a signup-preloaded-but-never-used
engine is still eventually freed by the existing idle-unload alarm —
previously it wasn't (see that fix's comment in `background.js`).

## Post-signup setup page — superseded

**Superseded by "Migrate to Claude API + Supabase" above** — onboarding no
longer waits on a model load at all; it's now a plain sign-up/sign-in form
(see `docs/architecture.md`'s `src/onboarding/` section). Left as
historical context for the no-AI-wording rule this section originated,
which still stands as a general product principle (`docs/product-spec.md`).

Right after the onboarding form is submitted, the page (same tab, no
navigation) now shows a dedicated setup screen instead of a plain
confirmation message — a progress bar (div-based, matching
`content.js`'s on-page badge visual) while the model loads, then one of:
ready (with an OK button that closes the tab), a friendly error with a
Retry button, or a friendly "can't finish on this device" message with
its own OK/Dismiss. None of this page's text mentions "AI"/"model"/
"WebGPU" — it's framed entirely as "setting up your job tracker." If the
model's already `"ready"` (e.g. a fast connection, or revisiting this page
later as Options) the wait is skipped entirely and the ready state shows
immediately. Closing the tab early doesn't cancel the load — `warmup()`'s
`enginePromise` lives in the Offscreen Document's own module scope (see
"Capture flow rewrite: single-click, consent-first" below), independent of
any page/tab.

Alongside this, the "ready" OS notification (`"Liber's on-device AI is
ready"`) and its supporting persistent flag
(`storage.js`'s former `hasNotifiedLlmReady`/`markLlmReadyNotified`) were
removed — the setup page now covers that, and the notification mentioned
"AI". The "not ready" notification (`showNotReadyPrompt`, shown during an
actual apply click before loading finishes) was kept, since it serves a
distinct, still-needed purpose, but reworded to drop "AI"/"model"/
"WebGPU" too.

The no-AI-wording rule was stated for this page specifically, but was
deliberately applied beyond it (the dashboard status pill, both OS
notifications) to keep it consistent extension-wide rather than leaving
one page as the odd one out — now a standing design principle, see
`docs/product-spec.md`.

## WebGPU software-adapter heuristic — superseded

**Superseded by "Migrate to Claude API + Supabase" above** — extraction no
longer touches WebGPU at all. Left as historical context.

Some devices (e.g. certain Chromebooks) expose a WebGPU adapter that
passes a plain truthiness check but is actually a slow software/emulated
renderer (SwiftShader, llvmpipe), not real GPU hardware — attempting to
load the model on one of these would "work" but be painfully slow.
`src/offscreen/offscreen.js`'s `checkWebGpuSupport()` (moved there from
`llmEngine.js` in the single-click, consent-first rewrite below) also
checks the adapter's
`GPUAdapterInfo` (`adapter.info`, or the older `adapter.requestAdapterInfo()`)
`vendor`/`architecture`/`device`/`description` strings against a short list
of known software-renderer names, and treats a match as `"unsupported"`
the same as no WebGPU at all. **Best-effort only** — there's no
standardized WebGPU API flag for "this is a software adapter," so an
unrecognized/future software renderer wouldn't be caught by this heuristic.

## Verified, no change needed

Three things double-checked against the vendored WebLLM bundle while
investigating first-load performance, confirmed already fine:

1. **Worker isolation.** `llmEngine.js` only ever runs inside the
   background service worker, never a page/content-script context (see
   `docs/architecture.md`), so a long generation can't freeze a page.
   WebLLM's bundle does include `Worker`/`postMessage`-based engine
   variants (`CreateWebWorkerMLCEngine`, `CreateExtensionServiceWorkerMLCEngine`),
   but adopting them would add a worker-within-the-worker for marginal
   benefit here — not adopted.
2. **Quantization.** `Qwen2.5-0.5B-Instruct-q4f16_1-MLC` (current) is
   already the smallest of WebLLM's four bundled quantizations for this
   model (944.62MB vs. 1060.2/1624.12/2654.75MB for `q4f32_1`/`q0f16`/
   `q0f32`).
3. **Cache usage.** WebLLM persists downloaded weights via the standard
   Cache API (`caches.open("webllm/...")`) on its own; nothing in this
   codebase touches `caches.*` directly, so nothing bypasses or clears it.

## Known gaps

- ~~Onboarding has no handler.~~ Fixed — `src/onboarding/onboarding.js` now
  saves the profile via `setProfile` on submit and prefills the form if a
  profile already exists.
- ~~Extension icons are missing.~~ Fixed — generated at
  `src/assets/icons/icon{16,48,128}.png` and wired into `manifest.json` and
  the notification icon in `background.js`.
- ~~`vendor/browser-polyfill.js` is missing.~~ Fixed — pinned
  `webextension-polyfill@0.12.0` is committed to `vendor/`. It was also only
  ever loaded in content scripts; it's now loaded in the background worker
  (via `import` in `background.js`) and in the dashboard/onboarding pages
  (via a `<script>` tag before their module scripts), since both call
  `browser.*` through `storage.js` and would otherwise throw on Chrome.
- The full view's sidebar no longer has a "Settings" entry point (the
  unwired placeholder link was removed) — the avatar's profile popover is
  read-only, so there's currently no way to edit profile info after
  onboarding.
- The apply-detected sound (`src/assets/notif.mp3`, played from
  `content.js`) fires on the "Apply" click itself, not on the native
  confirmation notification a moment later. Playing it from `background.js`
  instead isn't simple: on Chrome, the background runs as a service worker
  with no DOM, so it can't play audio directly, and routing it back through
  a message to the content script pushes playback far enough from the
  original click that browser autoplay restrictions can silently block it.
  Click-triggered is the reliable tradeoff for now — it means the sound can
  play even on the rare case the notification itself fails to show (e.g.
  notification permission blocked).

## Known issues: scraping (`content.js`) — historical, superseded

**Everything in this section describes the synonym-matcher era
(`findBySynonyms`/`FIELD_SYNONYMS`/`extractNearAnchor`), which no longer
exists.** Field extraction (`jobTitle`/`company`/`location`) now happens in
`background.js` via an on-device LLM (`src/shared/llmEngine.js`) — see
`docs/architecture.md`'s "Field extraction moved off content.js" and
"llmEngine.js" sections, and "Known limitations: on-device LLM scraping"
below for the tradeoffs that replaced the ones documented here. Left in
place as a record of what the synonym matcher's known issues were and how
they were fixed — the scope-resolution machinery it shares with the current
design (`findCardScope`/`findActiveCardScope`/`findLocalScope`,
`countVisibleJobTitles`, apply-click detection) is still live and still
described accurately below; only the final field-matching step it fed into
is gone.

All items below were fixed by replacing the per-site `PLATFORM_SELECTORS`
table with a synonym-driven, cross-site field matcher (`findBySynonyms`) and
extending card scoping to cover master-detail (list + detail-pane) layouts
(`findActiveCardScope`). See the updated `content.js` header comment and
`docs/architecture.md` for the new approach.

- ~~Brittle per-site selectors.~~ Fixed — `PLATFORM_SELECTORS` and
  `getPlatformKey()` are gone. Fields are now found by matching synonym
  words (e.g. "job-title"/"position"/"role") against stable attributes
  (`data-testid`, `data-test`, `aria-label`, schema.org `itemprop`) rather
  than exact, redesign-prone class names, so the scraper works on sites it
  was never specifically coded for.
- ~~Overly broad generic fallback selectors.~~ Fixed — the old
  catch-everything `[class*="company"]`-style `default` selectors are
  replaced by the same synonym matcher, with a max-plausible-text-length
  guard (`FIELD_MAX_LENGTH`) per field so a match can't swallow an unrelated
  wrapping container's text.
- ~~Apply-click detection is too loose, extension-wide.~~ Went through two
  iterations:
  1. First fix: dropped bare `"submit"` from a hardcoded `APPLY_KEYWORDS`
     phrase list, since the content script runs on `<all_urls>` (not just
     job sites) and "Submit" is one of the most generic, reused button
     labels on the web (newsletter signups, feedback forms, logins, search
     bars) — matching it alone meant the extension could fire
     `JOB_APPLY_DETECTED` on completely unrelated pages. (This was briefly
     reintroduced by hand during testing and had to be reverted — a live
     example of exactly the false-positive risk it addresses.)
  2. Current design: replaced the phrase list with
     `APPLY_KEYWORD_PATTERN = /\b(apply|submit)\b/i` — a word-boundary
     match on just the two root words instead of an exhaustive phrase
     list, so new phrasings ("Submit Your Application", "Quick Apply")
     work without a new list entry, and `\b` prevents false hits inside
     unrelated words like "resubmit" or "submitted". This deliberately
     reintroduces "submit" as a trigger word, on the reasoning that the
     empty-jobTitle guard added in the previous fix is a better mitigation
     for the false-positive risk than keyword-list surgery: a stray
     "Submit" click on an unrelated page almost never has anything
     synonym-matchable as a job title nearby, so no message gets sent
     either way. Known gap from dropping the phrase list: a button whose
     text is only "Send Application" (no literal "apply" or "submit" word)
     no longer matches — not seen in practice yet, flagged rather than
     special-cased back in.

  Residual risk either way: "apply"/"position"/"role" as bare words can
  still false-positive occasionally on job-adjacent wording elsewhere on a
  job site itself (e.g. "Apply filters", `aria-label="Email address"`) —
  acceptable tradeoff, not engineered around further for now.
- ~~Hostname matching uses substring, not exact match.~~ Moot — there's no
  more per-host selector table to match against, so `getPlatformKey()` (and
  its imprecise `host.includes(key)`) was removed entirely.
- ~~`companyFromUrl` slug extraction assumes a simple subdomain shape.~~
  Fixed — it now takes the *last* dot-segment before the known ATS suffix
  instead of the first, so extra subdomain levels (e.g.
  `eu.acme.myworkdayjobs.com`) resolve to `"acme"`, not `"eu"`.
- ~~`jobDescription` HTML stripping is a naive regex.~~ Fixed — replaced
  with `stripHtml()` (assigns to a detached element's `innerHTML`, reads
  back `.textContent`), which decodes entities correctly and can't be
  confused by literal `<`/`>` in text.
- ~~`locationFromLd`'s schema assumptions.~~ Fixed — `address` itself is now
  also unwrapped when it's an array, not just `jobLocation`.

### Follow-up patch: blind spots found during manual testing prep

A pre-test review of the redesign above surfaced four more concrete gaps,
all fixed in the same file:

- ~~Apply button's own accessible label could satisfy a synonym match on
  itself.~~ Fixed — `cardScope` is an ancestor of the clicked element, so
  `aria-label="Apply for this position"` on the Apply button itself would
  match the `jobTitle` synonym "position" and return "Apply Now" as the
  scraped title. `firstMatchText()` now skips any candidate that itself
  matches `isApplyTrigger()`.
- ~~`findActiveCardScope()` could pick unrelated page chrome.~~ Fixed —
  `document.querySelector` wasn't scoped to the job list, so a nav bar's
  active tab or pagination's `aria-current="page"` (which often has ≥3
  sibling page links too, passing the list-shape guard just as easily as
  a real job card) could win instead of the actual selected job card.
  `isNavigationChrome()` now excludes anything inside `nav`/`header`/
  `footer`/`[role="navigation"]`/pagination/breadcrumb containers.
- ~~Page-wide JSON-LD always took the first `JobPosting`.~~ Fixed — some
  listing pages embed one `JobPosting` per listed job for SEO, not just
  the one in view. `getJobPostingLd(scope)` now takes a `cardScope` and,
  when there's more than one candidate, prefers whichever posting's
  `title` actually appears in the clicked card's text over blindly taking
  the first one on the page.
- ~~`findCardScope`'s sibling check required an exact `className` string
  match.~~ Fixed — frameworks routinely vary a per-item modifier class
  (zebra striping, a "saved" badge), which made two genuinely repeated
  cards fail an exact string comparison and fall through to the riskier
  master-detail path unnecessarily. `sameCardShape()` now only requires
  the same tag and at least one shared class.

Residual, accepted risk: `findActiveCardScope()` still takes the first
*non-chrome* active-indicator match rather than ranking every candidate,
so an unrelated active element that also happens to live outside nav/
pagination (rare) could still be picked. Narrow heuristic, not a general
solution — flagged, not engineered around further.

### Bug found during live testing: LinkedIn company scraped as "Company reviews"

LinkedIn's job page has a generic "Company reviews" link (to its reviews
feature) whose own `aria-label`/class carries the bare word "company",
same as the real company-name element. Both were in the same `company`
synonym band, and the "Company reviews" link happened to win.

Root cause was the `broad` word "company" being tried in the same band as
every other candidate, with no way to prefer a more field-specific match
over a same-page element that merely mentions the field name generically.
Fixed by splitting `FIELD_SYNONYMS` into two tiers per field: `specific`
compound words (`"company-name"`, `"companyname"`, `"employer-name"`,
matching LinkedIn's actual `...__company-name` class) are now tried,
across both stable attributes and `id`/`class`, before the `broad` bare
words (`"company"`, `"employer"`, `"organization"`) are tried at all. A
generic link whose label merely contains the bare word "company" no
longer outranks the field's own compound-named element. Applied the same
`specific`/`broad` split to `jobTitle` and `location` too, for the same
reason — a bare "location" or "position" is just as capable of colliding
with unrelated same-page UI (a location filter, a "position available"
badge) as "company" was.

### Bug found during live testing: notification fires before the application is actually submitted

Multi-step apply flows — LinkedIn/Indeed/Glassdoor-style "Easy Apply,"
which opens a modal (resume, questions, review) before a final "Submit
application" step — matched `APPLY_KEYWORD_PATTERN` on *both* clicks: the
one that opens the modal, and the one that actually submits it. That meant
the "Save this job application?" notification could appear before the
user had filled out anything, and tapping "Save to Liber" on it would log
an application that was never actually sent.

Considered a timing-based fix first (wait briefly after a click to see if
it opened a `[role="dialog"]` modal, with a `pagehide` safety net for
direct-redirect apply flows that navigate away instead) — rejected as more
complex than needed. Fixed instead with `countVisibleJobTitles()`: before
doing anything else, the click handler counts distinct *visible* job
titles on the page (reusing the same synonym matching built for scraping).
More than one visible job title means we're still on a listing/search
view, not the final single-job submission step, so the click is skipped
entirely — no sound, no scrape, no message.

**First version broke on live testing.** `isVisible()` initially checked
`offsetParent` plus `[aria-hidden="true"]`/`[inert]` — a *layout*/ARIA
check, not a *visual occlusion* check. Reaching Indeed's final "Submit
application" step still didn't fire the notification; a diagnostic
console snippet confirmed the background search-results cards' titles
were still being counted as "visible," because Indeed overlays its Easy
Apply modal on top of the list without hiding or `aria-hide`-ing it —
`offsetParent`/`aria-hidden`/`inert` are hints the site has to bother
setting, and Indeed doesn't.

Fixed by rewriting `isVisible()` around `document.elementFromPoint()`
instead: it checks whatever's actually topmost at the element's on-screen
center point, which reflects the real stacking order regardless of the
site's ARIA hygiene — a modal's backdrop sits on top of background
content in virtually every real implementation (to block accidental
interaction with it) even when the site never marks that content
`aria-hidden`. Also naturally excludes a background card simply scrolled
out of the current viewport, as a side effect of checking the point
against `window.innerWidth`/`innerHeight`.

Known residual risk, not yet hit in testing: a true single-job,
direct-apply page (no modal at all) that also shows a "Similar jobs"
sidebar with several other titles would report >1 visible job titles and
get wrongly suppressed, even though it's an ordinary one-click apply with
nothing to wait for. If this turns up, the fix would need to scope the
count more narrowly (e.g. only within the main content area, or require
the duplicate titles to also look like repeated list items) rather than
counting every visible job-title-shaped element on the page.

## Capture flow rewrite: snapshot-and-refine — superseded

**This section's design (click-time card/landmark scoping,

replaced** by the defer-and-watch model described in "Capture flow
rewrite: defer-and-watch" below, now that extraction is an LLM that can

Left as historical context for why the snapshot-and-refine *state machine*

## Capture flow rewrite: snapshot-and-refine (supersedes the single-click gate above)

The previous fix for "notification fires before the application is
actually submitted" (above) was a single synchronous check
(`countVisibleJobTitles()`) at the moment of one click. That's inherently
limited — one click can't carry enough information to know whether a
multi-step flow is starting, continuing, or finishing. Replaced with a
small stateful flow, persisted per tab in `browser.storage.session` (not
an in-memory `Map` — `pendingByTab` didn't survive an MV3 service-worker
restart, a latent bug fixed as a side effect):

- An apply click with exactly one job visible (`countVisibleJobTitles() <=
  1` — **reused as-is** from the fix above) immediately captures a snapshot
  near the clicked anchor and prompts.
- An apply click with multiple jobs visible notes a flow *may* be starting
  (`LIBER_FLOW_PENDING`) but captures nothing yet and doesn't prompt.
- Every later Next/Continue/Review/Submit/Apply click sends whatever's
  nearest *that* click (`LIBER_FLOW_REFINE`) to merge into the flow —
  never a full-page scan, and never able to start a flow on its own, so a
  "Continue" button on a completely unrelated page does nothing.
- The prompt shows as soon as a snapshot first has real data (immediately
  on a single-job page, or on the first refine that produces something, if
  the flow started on a listing page). Already saved → later refines
  update that row (`updateJob`) instead of re-prompting. Already dismissed
  → later refines just update the stored snapshot silently.

See `docs/architecture.md` (`content.js`, `background.js`,
`src/shared/flowStorage.js`, `src/shared/fieldMerge.js`) for the full
design. Two consequences worth flagging:

- **Narrower extraction, on purpose.** The old page-wide fallback layer
  (`getJobPostingLd`, `getMetaContent`, `companyFromUrl`,
  `getOrganizationLd`, `cleanDocumentTitle`, `companyFromDocumentTitle`,
  `stripHtml`, and `scrapeJobDetails` itself) is deleted, not just
  unused — none of it is "selector/synonym matching near an anchor," which
  is incompatible with "never scan the whole page on a later step."
  Extraction is now purely proximity-based (`extractNearAnchor`,
  `findLocalScope`) everywhere, including the very first capture. Sites
  sparse on nearby synonym-matchable markup but rich in JSON-LD will
  capture less reliably than before this rewrite.
- **Scope narrowed to three fields.** `jobDescription` is no longer
  scraped at all; saved jobs now always have `jobDescription: ""`.

`findLocalScope`'s fallback when there's no repeated-card scope nearby
(the normal case on a plain single-job page) is a bounded local landmark
(`form`/`main`/`[role="main"]`/`article`, or a fixed small walk up the
tree) — deliberately never the whole document, even on the very first
capture. The alternative (fall back to the whole document only on the
first capture, never on a later refine) was considered and rejected in
favor of one consistent behavior everywhere.

## Capture flow rewrite: defer-and-watch — superseded

**Superseded by "Capture flow rewrite: capture-at-submit" below.** Extraction
no longer happens at every step a dialog/settle-window resolves to — it's
deferred all the way to the final submit click, specifically to move the
LLM's slowdown out of the mid-flow steps this section's design still ran
it on. Left as historical context for the scope-resolution primitives
(`findVisibleDialog`/`resolvePageScope`/`collectPageText`) that survive
unchanged, just called from a different point in the flow now — see the
new section for what changed and why.

The snapshot-and-refine model above still resolved a scope
*synchronously, at click time* — `findCardScope`/`findActiveCardScope` to
disambiguate a specific job card on a multi-listing page, or a landmark
walk otherwise — because the old field extractor needed a tightly-bounded
region. That's no longer necessary: the LLM can read whatever text is on
screen, so the click now always proceeds natively (no `preventDefault`,
no click-time scoping at all), and scanning happens once the real
single-job surface actually appears instead. See `docs/architecture.md`'s
"Defer-and-watch scanning" and the `background.js` section for the design
(`findVisibleDialog`/`resolvePageScope`/`watchForStepChange` in
`content.js`; the `tabs.onUpdated` listener + injected scanner in
`background.js`).

The save prompt's timing changed alongside this: it now waits for all
three fields (`jobTitle && company && location`) to be known, rather than
showing as soon as the first one is. New limitations/tradeoffs this
introduces, accepted for now:

- **Dialog/overlay detection is a heuristic, not a guarantee.** `[role="dialog"],
  [aria-modal="true"], dialog` covers well-built modals; the
  position/z-index/viewport-coverage fallback for modals without ARIA
  semantics can theoretically misfire on a large non-modal overlay (a
  promo takeover, a cookie banner covering ≥30% of the viewport) or miss a
  small/oddly-positioned real modal. Not seen in practice yet, flagged
  rather than engineered around further — same spirit as `isVisible()`'s
  existing accepted risk.
- **Non-modal, in-place step changes rely on a fixed settle window.**
  `watchForStepChange()`'s `SETTLE_WINDOW_MS` (2.5s) fallback is what
  covers an ATS wizard that swaps its form content in place with no dialog
  at all — if a given site's step transition is slower than that (a
  heavy client-side render, a network-bound step), the scan could fire a
  little early and catch stale/mid-transition content. Tunable if this
  shows up in testing.
- **`RECENT_FLOW_WINDOW_MS` (2 minutes) bounds cross-navigation/cross-tab
  scanning.** This is what keeps a `tabs.onUpdated` "complete" event from
  being treated as part of a flow the user has actually abandoned (closed
  the application tab, kept browsing in a tab that happens to share an
  old opener). Picked to comfortably cover realistic page-load/redirect
  timing without staying "live" so long that an unrelated later navigation
  in the same tab gets mistakenly scanned — not independently tuned
  against real ATS redirect latencies yet.
- **A flow that goes stale via the 30-minute TTL while its tab stays open
  gets no fallback prompt.** `tabs.onRemoved`'s last-resort "prompt with
  whatever we have" fallback (see `docs/architecture.md`) only fires on
  tab close — a genuinely abandoned-but-still-open tab just has its flow
  silently expire on the next `getFlow` read. MV3 has no persistent timer
  to drive a proactive check; accepted, since tab-close is the common,
  concrete signal that a flow is actually over.
- **The injected cross-navigation/cross-tab scanner
  (`liberScanInjectedPage`) is intentionally narrower than content.js's own
  scope resolution.** No overlay-heuristic fallback, no
  `countVisibleJobTitles`, no `MutationObserver`/settle-window — just
  dialog-or-landmark-or-body, once, right after the page reports
  `complete`. It can't `import` anything (`scripting.executeScript`'s
  `func` must be self-contained), so it's a deliberate, small duplication
  of content.js's logic rather than a shared helper — if one changes, the
  other may need the same change (both files cross-reference each other in
  a comment for this reason).

## Capture flow rewrite: capture-at-submit — superseded

**Superseded by "Capture flow rewrite: multi-step capture" below.**
Extraction no longer runs exactly once on the single final-submit click's
capture — every trigger click captures now, with extraction still only
running once, at commit time, over whichever of those captures are
actually needed. Left as historical context for why the final-submit-only
design existed and what specifically it got wrong (the problem that
prompted superseding it), and because `watchForContinuation`'s dialog
detection, `resolvePageScope`, and `collectPageText` all survive unchanged
from this section into the new one.

The defer-and-watch design above still ran `extractJobFields` on *every*
step a dialog appeared or a settle-window elapsed for — meaning the LLM's
real, user-visible slowdown (a genuine cost on low-end machines) landed
while the user was still filling the application in, not after. Rewritten
so extraction happens exactly once, at the final submit step, well after
the user has moved on: see `docs/architecture.md`'s "Capture-at-submit"
and the `background.js` section for the full design
(`FINAL_SUBMIT_PATTERN`/`watchForContinuation` in `content.js`;
`handleCandidateFinal`/`commitCandidate`/`tabs.onCreated` in
`background.js`; `src/shared/candidateStorage.js` replacing the old
`flowStorage.js`).

Consequences and new tradeoffs, accepted for now:

- **The old incremental field-merge across steps is gone.** `fieldMerge.js`'s
  `mergeSnapshot` is still used, but now only once per candidate (merging
  a partial JSON-LD read with the LLM's own output for that *same* final
  capture) rather than across every step of a multi-step flow. A field
  that's only discoverable on an *earlier* step and not visible at all on
  the final submit page would previously have been picked up there and
  carried forward; now it simply won't be captured. Not seen as a problem
  in practice yet (title/company/location are normally still visible on
  or near the final step), flagged rather than engineered around further.
- **`FINAL_SUBMIT_PATTERN` (`/\b(submit|apply)\b/i`) is narrower than
  `TRIGGER_PATTERN` on purpose, and that's a real, deliberate
  interpretation call, not something explicitly spelled out in what was
  asked for.** Without this split, every "Next"/"Continue" click in a
  non-modal, in-place multi-step wizard (no dialog, usually no new tab
  either) would get misclassified as "final" and run extraction
  prematurely, repeatedly — exactly the slowdown-during-the-flow problem
  this rewrite exists to fix. The known gap this introduces: a button
  whose label is only "Continue" but *is* genuinely the final action
  (rare) won't be captured at all. Not seen in practice yet.
- **The grace-period margin (`background.js`'s `EXTRACTION_GRACE_MS`,
  3.5s, vs. `content.js`'s `SETTLE_WINDOW_MS`, 2.5s) is a deliberately
  generous but still heuristic buffer against a real race.** Without it,
  `commitCandidate()`'s timer could fire while a
  `LIBER_CANDIDATE_SUPERSEDED` message is still in flight from
  `content.js`'s own dialog-watch, since both are async and can interleave
  at `await` boundaries on the same stored candidate. A sufficiently slow
  device/connection could in theory still lose the race even with the
  margin — not seen in practice yet, same spirit as this file's other
  accepted heuristics.
- **Cross-tab continuation no longer carries any data forward.** The old
  `copyFlow` merged a flow's partial snapshot into a brand-new tab opened
  mid-application (e.g. an ATS redirect). That's gone — a new tab opening
  from one with a pending candidate just supersedes (discards) that
  candidate; the new tab captures and commits entirely on its own. This is
  strictly simpler and loses nothing *for this design*, since there's no
  more incremental merging to carry across tabs either — flagged here
  only so the removal of `copyFlow` doesn't read as an oversight if
  compared against the old code.
- **A "Web Worker" was considered and deliberately not implemented.** The
  request that prompted this rewrite also asked to "run the model in a Web
  Worker so it does not freeze the page." Researched directly (not
  guessed): the vendored WebLLM bundle does expose worker-hosted-engine
  APIs (`CreateWebWorkerMLCEngine`/`WebWorkerMLCEngineHandler`,
  `CreateExtensionServiceWorkerMLCEngine`/`ExtensionServiceWorkerMLCEngineHandler`),
  but the latter — WebLLM's own extension-specific pattern — is designed
  for a *different* problem (a separate context like a popup or options
  page connecting to an engine that already lives in the background
  service worker, via `chrome.runtime.connect`), not for moving the engine
  off the service worker's own thread. Spawning a literal nested
  `new Worker()` *from inside* an MV3 extension service worker is
  genuinely unsettled territory — there's an open
  [whatwg/html issue](https://github.com/whatwg/html/issues/8362)
  specifically about whether workers/shared-workers should be creatable
  within a service worker at all, and extension service workers are
  explicitly called out there as a browser-specific exception each vendor
  can decide independently (not something to assume works). Since the
  engine already runs only inside the background service worker and never
  in a page/content-script context (see "Minimizing on-device LLM usage"
  and `docs/architecture.md`'s `llmEngine.js` section — this was true
  before this rewrite too), there's no page-freezing risk to solve by
  adding a nested worker, and doing so would add real, unverified risk for
  no demonstrated benefit. Not implemented; if Chrome's nested-worker
  support in extension service workers becomes a documented, stable
  capability later, this is the natural place to revisit it.

## Capture flow rewrite: multi-step capture — superseded

**Superseded by "Capture flow rewrite: single-click, consent-first"
below.** This design (and the "capture-at-submit"/"defer-and-watch"
designs before it) all tried to automatically detect "has the user
actually finished applying?" before extracting and prompting. The
replacement sidesteps that question entirely — capture once, ask the user
directly, extract only on "yes" — rather than inferring it from
continuation signals. Left as historical context for the real,
demonstrated problems each prior design hit (in particular, this one's own
late discovery that "same-tab reload" isn't a usable continuation signal
on a full-page-reload-per-step ATS, which directly informed abandoning
continuation-detection altogether rather than patching it further) — but
none of this section's machinery (grace-period timers, continuation
signals, cross-tab carryover, `attemptStorage.js`) exists anymore.

The capture-at-submit design above ran into the same class of problem
"defer-and-watch" was rewritten away from, just at a different single
point in the flow instead of at every step: capturing *only* the final
submit click's scope regularly missed the job title/company/location
entirely, because that information was only ever visible on the original
job-listing page or an earlier step — not on the final step's own modal/
form, which is usually just personal-info/resume fields by that point.
Deferring extraction to one single capture point didn't just defer the
LLM's slowdown (which was the actual goal, and stays true in this
rewrite too) — it also, as a side effect, deferred which page's content
backing it, and that page is often the wrong one for the fields that
matter.

The fix is **not** a reversion to defer-and-watch's incremental-LLM-every-
step model. It's the previous "single capture" model generalized to
"every trigger click captures, but extraction still only ever runs once,
at commit time, over whichever of the accumulated captures are actually
needed" — see `docs/architecture.md`'s "Multi-step capture,
commit-on-true-finality" and "Commit-time resolution" sections, and the
`background.js` section, for the full design
(`LIBER_CAPTURE_STEP`/`LIBER_CONTINUATION_SIGNAL` in `content.js`;
`handleCaptureStep`/`markContinuation`/`carryOverAttempt`/`commitAttempt`
in `background.js`; `src/shared/attemptStorage.js` replacing
`candidateStorage.js`; the new `src/shared/snapshotResolution.js`).

Consequences and new tradeoffs, accepted for now:

- **`FINAL_SUBMIT_PATTERN` is gone — every trigger click now captures,
  not just "Submit"/"Apply".** This directly removes the previous
  design's own flagged gap (a "Continue"-only final action never being
  captured), since there's no longer a distinction between a "final" and
  "continuing" click at capture time at all. The cost: every click near a
  job application now does a synchronous DOM read
  (`collectJobPostingLd`/`collectPageText`), not just the one that turns
  out to be last. Accepted — these reads were already cheap and
  synchronous under the previous design too, just gated behind a pattern
  check that's now removed.
- **A real same-tab top-level reload needs its own detection again**
  (`background.js`'s new `tabs.onUpdated` listener), since
  `content.js`'s own instance doesn't survive that kind of navigation —
  this is the one piece of defer-and-watch's deleted `tabs.onUpdated`
  machinery that had to come back. Unlike defer-and-watch's version,
  though, this one does **not** bring back the injected
  `scripting.executeScript` cross-navigation scanner (`liberScanInjectedPage`)
  or the `scripting` permission it needed — it's purely a
  "cancel the pending timer, don't commit yet" signal; no re-scraping
  happens from this listener at all. The new/reloaded page's own
  `content.js` instance captures its own next step normally, from its own
  next trigger click. This also means `RECENT_FLOW_WINDOW_MS`-style
  bounding (defer-and-watch's 2-minute guard against scanning a navigation
  far outside any real flow) isn't needed here either — there's nothing
  to scan, so a stray `tabs.onUpdated` firing on an unrelated tab/
  navigation just costs one cheap, no-op `storage.session` read
  (`markContinuation` bails immediately if that tab has no `"capturing"`
  attempt).
- **SPA soft-navigation (`history.pushState`/`replaceState`/`popstate`)
  is treated as a continuation signal, same as a dialog appearing** —
  many real ATS wizards (LinkedIn Easy Apply, Workday) move between steps
  via client-side routing with no dialog and no real top-level
  navigation at all; without this, those steps' "Next"/"Continue" clicks
  would misfire as final the moment the grace period elapsed. The patch
  is installed once, at `content.js`'s module load, not per-click, to
  avoid stacking wrapper functions around `history.pushState`/
  `replaceState` on every trigger click for the page's whole lifetime.
- **Cross-tab continuation carries data forward again — the old
  `copyFlow` behavior is effectively back, with one deliberate change.**
  capture-at-submit's "no copy, new tab starts fresh" tradeoff is
  reversed: `attemptStorage.js`'s new `copyAttempt` carries the
  accumulated steps into the new tab (`background.js`'s
  `carryOverAttempt`), since an ATS redirect to a new domain is exactly
  the case where the original job-listing page's info (captured in the
  old tab) would otherwise be lost for good. Unlike the original
  `copyFlow`, though, the opener's own copy is explicitly cleared after
  the copy, rather than left alive alongside the new tab's — two live
  "capturing" attempts for what's logically one application could
  otherwise each independently arm their own commit timer and each
  independently extract/show a Save prompt for the same real application.
  Bounded by a new `CARRYOVER_WINDOW_MS` (2 minutes, unverified/not
  measured against real ATS redirect timing, same caveat as
  defer-and-watch's old `RECENT_FLOW_WINDOW_MS`) so an effectively-
  abandoned attempt can't incorrectly attach itself to an unrelated new
  tab opened much later from the same opener.
- **A "capturing" attempt can now persist indefinitely, which the
  tab-close handling (`tabs.onRemoved`) has to account for.** Under
  capture-at-submit, an `"awaiting-finality"` candidate was never
  realistically alive for longer than the few-second grace window, so
  `tabs.onRemoved` could safely just leave it alone and let the timer
  fire on its own. That's no longer safe: a continuation signal (a
  dialog, a new tab, or — only right after the very first captured step,
  see the reload fix below — a same-tab reload) can leave a `"capturing"`
  attempt waiting indefinitely for a trigger click that never comes.
  Closing the tab is the signal this project already treats as "the user
  is done here" elsewhere (same `tabs.onRemoved` listener, same
  reasoning as its "ready" branch), so it now also forces a commit of
  whatever was accumulated for a still-"capturing" attempt, instead of
  letting it silently rot until the 30-minute TTL drops it. The remaining
  gap this doesn't close: an attempt abandoned mid-flow with its tab left
  open (no further click, no close either) still only cleans up via that
  same TTL, same as every prior design.
- **A same-tab reload only blocks a commit right after the very first
  captured step — found necessary, not just theoretical.** The first
  version of this rewrite treated *any* same-tab reload the same as a
  dialog or new tab: unconditionally "still continuing." That broke on a
  real ATS tested live (Indeed's `smartapply.indeed.com`): it reloads the
  page on *every* step, including the genuinely final one, so the
  attempt never committed at all — it just sat in `"capturing"` forever
  (only recoverable via the `tabs.onRemoved` tab-close fallback above,
  which the user doesn't always trigger right away). `markContinuation`
  now only treats `"same-tab navigation"` as blocking when
  `attempt.steps.length <= 1` (i.e. this reload followed the very first
  captured step, which typically *is* just the listing-page Apply click
  carrying the user into the actual application) — past that, a reload
  is ignored as a signal entirely, and only a dialog or a new tab still
  block. The real, accepted cost this introduces: on a full-page-reload
  ATS like this one, the save prompt can now fire after an *intermediate*
  step too (whichever step's own grace-period timer isn't cancelled by
  anything else), not only the true final one — contradicting this
  project's own standing "don't interrupt the user mid-fill" goal for
  that specific site shape. Accepted deliberately: `handleCaptureStep`
  carries the accumulated `steps` forward from a `"ready"` attempt (not
  just `"capturing"`) specifically so a premature prompt the user ignores
  or dismisses doesn't lose anything — the user can keep applying, the
  next capture reopens the same attempt from where it left off, and a
  later, truly-final commit re-resolves over the *full* accumulated step
  list, not just whatever was captured after the premature one. No
  heuristic was found that reliably tells "an intermediate step's reload"
  apart from "the final step's reload into a confirmation page" on a site
  that reloads identically for both — flagged here rather than guessed
  around further.
- **No cap on how many steps one attempt can accumulate.** A pathological
  or buggy multi-step flow (or a user repeatedly clicking a trigger
  element that never actually advances anything) grows `attempt.steps`
  without bound until either a commit or the 30-minute TTL clears it.
  Bounded organically by human click speed in practice; not seen as a
  real problem, flagged rather than engineered around with a cap that has
  no concrete failure mode driving its choice of limit yet.
- **No de-duplication of near-identical consecutive steps** (e.g. a
  literal double-click on the same button, or a click that doesn't
  actually change the page at all). Harmless under
  `resolveAttemptSnapshot`'s short-circuiting walk — a near-duplicate step
  either gets skipped the same way any other already-complete-snapshot
  step would, or costs one redundant (but cached, by URL) LLM call in the
  worst case — so not engineered around either.

## Capture flow rewrite: single-click, consent-first (supersedes multi-step capture above)

Every prior design in this history tried to infer "has the user actually
finished applying?" automatically, and every one of them needed
increasingly fragile machinery to approximate that one question (grace
timers, continuation signals, cross-tab carryover, reload-vs-dialog
heuristics tuned per-ATS). This rewrite stops trying to infer it: capture
once, scoped tightly to the specific job, ask the user directly — "Save
this job to your tracker?" — before touching the model at all, and only
extract/save on "yes." See `docs/architecture.md`'s "Single-click,
consent-first capture," "Scope resolution," and the `background.js`/
`src/offscreen/` sections for the full design
(`resolveSingleJobScope`/`resolveMultiJobScope`/`findRepeatedCardAncestor`
in `content.js`; `handleSaveRequested` in `background.js`; the Offscreen
Document + Worker split between `llmEngine.js` and `src/offscreen/`).

This also moves the LLM out of the background service worker and into a
Worker hosted inside a `chrome.offscreen` Document — researched and
confirmed directly against the vendored `vendor/web-llm.js` bundle that a
literal `new Worker()` cannot be created inside an MV3 extension service
worker (unresolved spec territory: `w3c/webextensions#287`,
`whatwg/html#8362`), but a genuine Worker *can* be created from an
Offscreen Document, using WebLLM's already-exported
`CreateWebWorkerMLCEngine`/`WebWorkerMLCEngineHandler` pairing. A
dead-end sibling API, `CreateExtensionServiceWorkerMLCEngine`/
`ExtensionServiceWorkerMLCEngineHandler`, looked like it might fit instead
but doesn't — its handler always builds its own fresh internal engine and
can't be handed an already-constructed Worker-hosted one, confirmed
directly in the vendored source. Flagged here so this dead end isn't
rediscovered.

Consequences and new tradeoffs, accepted for now:

- **No more "did they actually finish" detection at all.** The entire
  point of this rewrite is to stop trying. The tradeoff: a user who clicks
  "Apply" and accepts the consent prompt, then abandons the application
  partway through, still gets a saved job record — there's no way to
  distinguish "applied" from "started and gave up" anymore. Accepted
  deliberately: the user explicitly confirmed intent to track the job, and
  the existing dashboard status field (`applied`/`interviewing`/
  `rejected`/`ghosted`) already lets them correct this manually if it
  matters to them. Not solved here.
- **Repeat-prompt suppression is in-memory only, resetting on any real
  page reload.** A multi-page (non-SPA) wizard that reloads between every
  step will show the consent prompt again on each page, not just once for
  the whole flow — each prompt captures and (if accepted) saves
  independently, relying on `addJob`'s existing composite-key dedup to
  harmlessly no-op a repeat save of the same job. Revisit if real-world
  testing shows this is more annoying than expected. **Narrower exception,
  added later:** an *unanswered* prompt specifically (not yet "yes"/"no")
  does now survive a same-tab redirect or a new tab the trigger click
  opened — `background.js`'s `pendingConsentByTab` (reported via
  `LIBER_CONSENT_PENDING`/`LIBER_CONSENT_RESOLVED`, claimed via
  `LIBER_CHECK_PENDING_CONSENT`) hands the exact same captured
  `{url, scopeText, structuredSnapshot}` to whichever page asks first,
  bounded by a 2-minute TTL and cleared the instant it's answered or its
  tab closes. Deliberately still narrow: this only ever resumes one
  already-shown, still-unanswered prompt — it does not merge/accumulate
  captures across steps the way the old per-tab flow-tracking designs did,
  and a *reload after answering* still isn't covered (nothing's pending by
  then). See `docs/architecture.md`'s `background.js` section.
- **Repetition-detection thresholds are unmeasured.**
  `CLASS_OVERLAP_THRESHOLD` (0.5), `MIN_CARD_TEXT_LENGTH` (40),
  `MAX_REPEAT_WALK_DEPTH` (8) are reasoned defaults, not tuned against a
  broad sample of real listing markup (LinkedIn/Indeed/Glassdoor/
  ZipRecruiter-style search results all differ). Same "accepted risk,
  bounded, not derived from measurement" spirit as this file's other
  heuristic constants (e.g. the old `RECENT_FLOW_WINDOW_MS`/
  `CARRYOVER_WINDOW_MS`, now both gone along with everything else they
  guarded).
- **WebGPU access from an Offscreen Document was expected, not explicitly
  verified against Chrome's documentation during research** — Offscreen
  Documents are real page contexts, and WebGPU has long been available to
  ordinary extension/web pages independent of Chrome 124's
  service-worker-specific grant, but this should be the literal first
  thing checked when testing this build (load `offscreen.html`, confirm
  `navigator.gpu`/`requestAdapter()` succeed) before trusting anything
  downstream of it.
- **A mid-save tab close falls out "for free" with no special-casing** —
  `handleSaveRequested`'s promise chain doesn't depend on the tab staying
  open, so a closed tab just means the result push fails and falls
  through to the OS-notification fallback. Worth calling out explicitly
  since the *previous* design needed a dedicated `tabs.onRemoved`
  force-commit branch to get the same guarantee — this one doesn't, simply
  because there's no longer any open-ended waiting state for a tab close
  to have to resolve.
- **`src/shared/attemptStorage.js` and `src/shared/snapshotResolution.js`
  are deleted, not simplified-and-kept.** Earlier drafts of this rewrite
  considered keeping a trimmed single-record version of each, but there's
  genuinely nothing left to persist (no steps to accumulate, no walk to
  orchestrate) — the entire JSON-LD-then-LLM-if-needed merge is ~6 lines,
  inlined directly into `background.js`'s `handleSaveRequested`.

### Bug found after shipping the offscreen split: the engine silently never loaded

The Offscreen Document + Worker split (above) broke the engine completely
for one release — `warmup()` always resolved to a no-op, `liber_llm_status`
never left `{}`, and the setup page just sat on "Downloading…" forever,
with no visible error anywhere (the service worker goes dormant between
messages, taking its console buffer with it).

Root cause, confirmed directly in a live `offscreen.html` console: **Chrome
only exposes `chrome.runtime` to Offscreen Documents, not `chrome.storage`**
(`typeof chrome.storage` → `"undefined"` there) — deliberate on Chrome's
part, so an offscreen document can't double as a background-page
replacement. `offscreen.js`'s `setLlmStatus()`/`getLlmStatus()` calls (via
`llmStatus.js`) threw on `browser.storage.session` every time, aborting
`loadEngine()` before it reached the model at all. Worked fine before this
split because the engine then ran directly in the background service
worker, which does have `chrome.storage`.

Two smaller bugs compounded this into "no errors anywhere": `background.js`'s
`onMessage` listener was `async` (so it always returned a Promise, even for
message types it didn't handle, racing out `offscreen.js`'s real response —
see `docs/architecture.md`'s `background.js` section), and `warmup()` was
called fire-and-forget with no `.catch()`, so the real exception became a
silent unhandled rejection.

Fixed by having `offscreen.js` keep status in a local variable and relay
every change to `background.js` via `LIBER_OFFSCREEN_STATUS` —
`background.js` is the only context that writes to `liber_llm_status` now.
See `docs/architecture.md`'s `llmStatus.js` section for the current design.

## Known limitation: synonym matching doesn't generalize to every site — superseded

This entire section describes the synonym matcher, which has been replaced
by on-device LLM extraction (see the note at the top of "Known issues:
scraping" above). Left as historical context for *why* that replacement
happened — the LLM approach was chosen specifically to remove this
limitation (coverage no longer depends on a site exposing the right
markup) — but see "Known limitations: on-device LLM scraping" below for
what replaced it.

Not a bug to fix — an accepted property of the site-agnostic approach
(`findBySynonyms`, see `docs/architecture.md`). It works by recognizing
synonym words in stable attributes/`id`/`class`/schema.org microdata near
the clicked anchor, which means it only works as well as a given site's
markup happens to expose that structure. Sites differ a lot here: some
carry `JobPosting` microdata throughout (most reliable), some use
`data-testid`/`aria-label` hooks with recognizable naming, and some render
job details as plain styled text with no semantic hook connecting a
`<div>` to "company" or "location" at all — there's nothing for a synonym
match to find on that last kind of site, regardless of how the synonym
list is tuned.

This is sharpest for anything like a full job *description* specifically —
free-form long-form content is the field least likely to carry a
consistent semantic hook across sites, which is a real part of why
`jobDescription` isn't scraped at all right now (see "Capture flow
rewrite" above) rather than only "proximity-only extraction is
incompatible with it." Reintroducing it (see "Near-term" below) will hit
this same ceiling — expect a non-trivial fraction of sites where no
description gets captured even when title/company/location all do.

The per-site selector table this replaced (`PLATFORM_SELECTORS`) would
have scraped any one *known* site more reliably, at the cost of needing a
new table entry (and maintenance as sites redesign) for every site not yet
covered — the opposite tradeoff. Not revisiting that tradeoff for now;
flagged here so a "why doesn't this work on site X" report isn't mistaken
for a regression.

## Known limitations: on-device LLM scraping — superseded

**Superseded by "Migrate to Claude API + Supabase" above** — none of these
tradeoffs apply to a server-side Claude call (no device/WebGPU requirement,
no multi-hundred-MB download, no Offscreen Document/Worker lifetime cost).
See the "Consequences of moving extraction server-side" list in
`docs/architecture.md`'s `extraction.js` section for what replaced them.
Left as historical context for what the on-device design's tradeoffs
actually were.

What replaced the synonym matcher's limitations above — these were the
tradeoffs of the on-device design (`src/shared/llmEngine.js`,
`src/offscreen/`, `src/shared/llmStatus.js`, all since deleted), accepted
for now rather than engineered around:

- **Chrome/Chromium-only — and currently total, not just scraping.** The
  engine requires WebGPU, which Firefox's support is still inconsistent/
  behind flags on many platforms. There is deliberately no fallback to the
  old synonym matcher (see `docs/architecture.md`'s "Required LLM, no
  fallback"), so scraping simply doesn't work on Firefox today, despite
  `manifest.json` still shipping `browser_specific_settings.gecko`. On top
  of that, `manifest.json`'s `background` block had a pre-existing,
  unrelated bug (both `service_worker` and the MV2-only `scripts` key
  present at once — invalid under `manifest_version: 3`) that silently
  stopped the service worker from registering on Chrome at all; fixing it
  meant removing `scripts`, which Firefox's own MV3 implementation
  currently relies on instead of `service_worker`. So right now
  `background.js` — onboarding's auto-redirect, flow tracking,
  notifications, all of it, not just the LLM path — doesn't run on
  Firefox at all. Revisit both if/when Firefox's WebGPU support matures
  and/or its `service_worker` support is reliable enough to rely on.
- **First-run model download.** Even at the current, deliberately small
  model (`Qwen2.5-0.5B-Instruct-q4f16_1-MLC`, ~945MB — see "Model size vs.
  accuracy" below), this is still a real download, fetched once and cached
  by WebLLM. Surfaced as a genuinely rough first-install experience during
  manual testing on a slow/public connection — watching a stuck-looking "0%"
  for several minutes reads as broken even when it's actually progressing
  normally underneath. Mitigated, not eliminated: `onboarding.js` triggers
  the load as early as page load (not gated on submit), and the post-signup
  setup page (see "Post-signup setup page" above) shows live progress — or
  immediately shows "ready" if already cached, skipping the wait — without
  requiring the user to keep checking back. A user who applies to something
  within that first window still hits the "Liber can't scrape this
  application yet" notice regardless.
- **Offscreen Document / Worker lifetime cost.** The engine is now
  module-level state in `src/offscreen/offscreen.js`'s Worker
  (`llmWorker.js`), not the background service worker — created on demand
  by `llmEngine.js`'s `ensureOffscreenDocument()` and not proactively torn
  down, but still not guaranteed to survive indefinitely. The weight files
  stay cached (Cache API), so recovery is a reload (re-instantiate WASM,
  re-upload weights to the GPU) rather than a re-download, but it still
  adds a few seconds of latency to whichever request triggers it. Not
  solved — not expected to matter much in practice given the engine is
  unloaded immediately after every request anyway (see "Minimizing
  on-device LLM usage" in `docs/architecture.md`).
- **Device/hardware requirements.** Even on Chrome, WebGPU access depends on
  the device having a capable GPU and driver — a low-end or virtualized
  machine may report `navigator.gpu` as unsupported, or fail partway through
  loading. Both surface as the same "not ready" notification as a slow
  download; there's no separate messaging distinguishing "will never work
  on this device" from "still loading," beyond the `unsupported` vs
  `loading`/`error` states already in `llmStatus.js`. A detected-but-slow
  *software* adapter (passes the truthiness check but is CPU-emulated) is
  now also folded into `unsupported` — see "WebGPU software-adapter
  heuristic" above.
- **New failure mode: wrong-but-well-formed output, not just missing
  output.** The old matcher's failure mode was silence — no synonym match,
  empty field. An LLM's failure mode can instead be a plausible-looking but
  wrong value. Mitigated, not eliminated, by the schema-constrained JSON
  output (guarantees *shape*, not *correctness*) and the system prompt's
  explicit "use `\"\"` if you're not sure, never guess" instruction — not
  independently verified against a held-out set of real job pages yet.
- **Latency moved, not removed.** Resolving `scopeText` into a snapshot
  takes a real amount of time (model inference), always paid inside the
  Offscreen Document's Worker, relayed through `background.js`, instead of
  synchronously in `content.js` — deliberately so it never delays the
  click's own page navigation (see `docs/architecture.md`'s data-flow
  diagram). Since "Capture flow rewrite: single-click, consent-first"
  above, it's also moved in *when*: it's only ever paid once the user has
  explicitly accepted the "Save this job to your tracker?" prompt, never
  speculatively, surfaced via the "doing some work" popup rather than the
  prompt itself visibly lagging a click.

### Model size vs. accuracy

Started on `Qwen2.5-3B-Instruct-q4f16_1-MLC` (~2.5GB-class GPU footprint);
switched to `Qwen2.5-0.5B-Instruct-q4f16_1-MLC` (~945MB) after manual
testing showed the 3B's download was painful enough on an ordinary (let
alone slow/public) connection to be a real first-install UX problem — see
"First-run model download" above. WebLLM's prebuilt list (checked directly
against the vendored `vendor/web-llm.js`, not from memory) by GPU-memory
footprint, a reasonable proxy for download size:

| Model | Footprint |
|---|---|
| SmolLM2-135M-Instruct | ~360MB |
| SmolLM2-360M-Instruct | ~376MB |
| Llama-3.2-1B-Instruct | ~879MB |
| **Qwen2.5-0.5B-Instruct (current)** | **~945MB** |
| Qwen2.5-1.5B-Instruct | ~1.63GB |
| Qwen2.5-3B-Instruct (original) | ~2.5GB |

Picked Qwen2.5-0.5B over the smaller SmolLM2 options at a similar
footprint because Qwen2.5's small sizes are specifically known for holding
up better on instruction-following/structured-extraction tasks — this is
general reputation, not something independently benchmarked against
Liber's actual extraction prompt.

Grammar-constrained JSON output (`response_format: { type: "json_object",
schema }`, see `src/offscreen/offscreen.js`) guarantees valid `{jobTitle,
company, location}` *shape* at any model size — what degrades going
smaller is *correctness*: picking the right entity out of messy scraped
text instead of hallucinating or grabbing nearby-but-wrong text (see "New
failure mode" above). Not yet measured concretely for this task at 0.5B
specifically. **If real-world accuracy turns out unreliable at this size,
the documented next step is `Qwen2.5-1.5B-Instruct-q4f16_1-MLC`** (same
model family, one size up) before reconsidering 3B — just change
`MODEL_ID` in `src/offscreen/offscreen.js`, nothing else in the pipeline
depends on which size is loaded.
